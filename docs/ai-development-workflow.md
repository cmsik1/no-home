# AI 협업 개발 워크플로

이 문서는 팀에서 기획, 요구사항, API, 아키텍처, ERD와 담당 작업이 확정된 이후 AI와 구현 작업을 진행하는 기준을 설명한다. Jira를 작업 상태의 기준으로 사용하며, 문서화 자체가 구현의 병목이 되지 않도록 필요한 기록만 남긴다.

## 문서 구조

```text
CHANGELOG.md
docs/
  work/
    NOHOME-123-short-title/
      README.md
      plan.md
  adr/
    0001-short-title.md
  architecture/
    pipeline.md
```

- Jira: 담당자, 우선순위, 진행 상태와 완료 조건을 관리한다.
- `plan.md`: AI가 구현 전에 읽는 작업 계획이다.
- 작업별 `README.md`: 사람이 빠르게 확인할 작업 목적, 주요 변경과 결과이다.
- ADR: 오래 유지될 중요한 기술 결정을 내린 이유와 영향을 기록한다.
- `CHANGELOG.md`: 배포되거나 프로젝트에 반영된 주요 변경사항을 기록한다.
- Git: 실제 코드 변경 이력을 보존한다.

`workflow.md`와 `roadmap.md`는 저장소에 두지 않는다. 반복 작업 절차는 개인 Codex Skill로 재사용하고, 작업 순서와 상태는 Jira에서 관리한다.

## 문서를 만드는 기준

다음 중 하나에 해당하면 `docs/work/<JIRA-KEY>-<slug>/`에 `README.md`와 `plan.md`를 만든다.

- 여러 파일이나 계층을 함께 변경한다.
- DB 스키마, API 계약 또는 기능 정책을 변경한다.
- 새로운 기능이나 중요한 데이터 파이프라인을 구현한다.
- 작업을 중단한 뒤 다른 사람이 이어서 수행할 가능성이 있다.

오탈자, 단일 파일의 단순 수정처럼 맥락이 작은 작업은 Jira와 Git 기록만 사용한다.

ADR은 기술 선택이 장기간 구조에 영향을 주거나 되돌리기 어려울 때만 작성한다. `CHANGELOG.md`에는 모든 커밋이 아니라 사용자가 인지할 기능, 호환성, 데이터 또는 운영상의 주요 변경만 기록한다.

## 사용 시나리오

1. AI가 Jira 작업과 연결된 명세를 읽고 범위, 의존성, 완료 조건을 확인한다.
2. 문서 생성 기준을 만족하면 작업 폴더의 `README.md`와 `plan.md`를 작성한다.
3. AI가 구현 계획과 자동 테스트·블랙박스 테스트 시나리오를 제시하고 멈춘다.
4. 사용자가 계획을 승인하면 AI가 구현과 자동 테스트를 수행한 뒤 다시 멈춘다.
5. 사용자가 실제 서비스에서 로그인 같은 블랙박스 테스트를 수행하고 결과를 알려준다.
6. 실패하면 구현 단계로 돌아가고, 성공하면 사용자의 마무리 지시에 따라 문서를 갱신한다.
7. 중요한 기술 결정은 ADR에, 프로젝트의 주요 결과는 `CHANGELOG.md`에 반영한다.
8. 별도로 Jira 변경 권한을 받은 경우에만 결과와 검증 내용을 요약하고 상태를 갱신한다.

기본적으로 계획 승인, 구현 결과 확인, 블랙박스 테스트와 최종 문서 반영 사이에는 각각 사용자 확인이 필요하다. 다만 사용자가 특정 범위에 대해 연속 진행 권한을 명시한 경우에는 그 범위 안에서 확인 단계를 묶어 진행할 수 있다.

예시:

```text
Jira: NOHOME-123 소셜 로그인 전환
문서: docs/work/NOHOME-123-social-login/
브랜치: codex/NOHOME-123-social-login
커밋과 PR 제목: NOHOME-123 포함
```

Jira 연동을 사용할 수 없으면 사용자가 제공한 이슈 내용으로 같은 절차를 수행하고, Jira 상태 변경 단계만 생략한다. AI는 사용자 확인 없이 이슈 생성, 상태 변경 또는 댓글 작성을 하지 않는다.

## 기존 문서 처리 원칙

과거 AI 작업 기록은 `docs/archive/artifact/docs/AI/sprints/`에 원형 보존한다. 현재 코드와 일치하는 기준 문서만 `docs`의 현재 문서 영역에서 관리한다.

개인 학습 기록과 공개하지 않을 메모는 `.private/`에 두며 Git에 포함하지 않는다.
